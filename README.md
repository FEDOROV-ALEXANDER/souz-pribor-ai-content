# AI-помощник для подготовки товарных описаний (КИП)

Локальный MVP: по JSON о контрольно-измерительном приборе генерирует черновик карточки товара для B2B-каталога. Результат проходит пост-валидацию — технические характеристики сверяются с входом кодом, а не доверием к модели.

## Что здесь реализовано (за 10 секунд)

- **Два интерфейса**: CLI (`python -m src.cli ...`) и FastAPI endpoint (`POST /generate`).
- **Две LLM-платформы**: локальная Qwen 3.8 27B (llama-server) и облачная `nvidia/nemotron-3.5-lightning:free` через OpenRouter — переключение только `.env`, без правки кода. Rate-limit OpenRouter (пауза ≥4 с) соблюдается кодом.
- **Guardrail против выдумывания**: `key_specs` собирается кодом из входа; каждое значение `specs` сверяется с `seo`-полями; схема и длины — Pydantic; при ошибках — один correction-проход с лимитом попыток.
- **Docker** — бонус: `docker build -t souz-pribor .` и `docker run -p 8000:8000 --env-file .env souz-pribor`.
- **Честность про данные**: в задании один пример структуры; второй товар — явно подписанный демонстрационный fixture.
- **16 тестов** на валидацию и пайплайн; пакетный прогон `--all` — аналог мини-replay.

## Что делает сервис

- Принимает JSON о товаре (CLI-файл или `POST /generate`).
- Передаёт данные в LLM через OpenAI-compatible API (локальная Qwen или OpenRouter).
- Формирует черновик: `seo_title` (до 70 символов), `seo_description` (800–1200 символов), `key_specs`, `search_queries` (3–5), `commercial_block`, `missing_fields`, `warnings`, `validation`.
- Ключевые характеристики собирает **код из входа** — модель их не переписывает.
- При невалидном ответе LLM делает один correction-проход с перечнем ошибок, далее честный отказ.

## Быстрый запуск

```bash
uv sync
cp .env.example .env   # при необходимости поправить адрес/модель
uv run python -m src.cli data/product_1.json --format markdown
uv run python -m src.cli data --all --format markdown --out examples   # пакетный прогон
uv run uvicorn src.main:app --reload                                    # API на :8000
```

Docker (бонус, не требуется заданием):

```bash
docker build -t souz-pribor .
docker run -p 8000:8000 --env-file .env souz-pribor
```

## Конфигурация LLM

Всё через `.env` (в `.gitignore`, ключ не в коде):

```text
# Локальный llama-server (по умолчанию)
LLM_BASE_URL=http://127.0.0.1:8080/v1
LLM_API_KEY=not-needed-for-local
LLM_MODEL=qwen3.8-27b-iq4xs
LLM_TIMEOUT_SECONDS=180
LLM_MIN_REQUEST_INTERVAL_SECONDS=0
```

Переключение на OpenRouter-бесплатные модели — поменять `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL` и поставить `LLM_MIN_REQUEST_INTERVAL_SECONDS=4.5`. Пауза между запросами соблюдается кодом. Проверено на `nvidia/nemotron-3.5-lightning:free`; другие актуальные бесплатные варианты: `google/gemma-4-26b-a4b-it:free`, `liquid/lfm-2.5-2.6b:free` (бывшие `meta-llama/llama-3.3-70b-instruct:free` и `qwen/qwen3-32b:free` на OpenRouter уже платные).

## Пример входа и выхода

Вход — `data/product_1.json` (из задания), `data/product_2.json` (демонстрационный fixture по той же схеме: в задании приложен один пример структуры, второй товар не предоставлен). Выходы — `examples/product_1_result.md`, `examples/product_2_result.md`.

## Почему такой промпт

System-промпт задаёт роль, запреты (не выдумывать характеристики, материалы, сертификаты, ГОСТ, цены, наличие), требование «данных нет» при пробелах, длины полей, деловой стиль без клише («лучший», «идеальный»), жёсткий JSON по схеме. User-промпт подставляет входной JSON целиком — модель не догадывается, чего «не хватает». Correction-промпт возвращает модели её же ответ с перечнем ошибок.

## Как защищаемся от выдуманных характеристик

1. `key_specs` собирает код из входного `specs` — искажение исключено структурно.
2. Каждое значение `specs` обязано встретиться в `seo_title`/`seo_description` (с нормализацией тире/запятых; для «число + единица» требуется их совместное присутствие — переписанное число не проходит по одной общей единице).
3. Схема Pydantic: длины, 3–5 запросов, обязательные поля.
4. Запрещённые клише.
5. Один correction-проход; при повторном провале — ошибка, а не «почти подходящий» текст.

## Обработка ошибок

- Битый входной JSON — понятное сообщение CLI, 422 в API.
- Пустой `specs` — `key_specs` пуст, предупреждения, блок характеристик помечен «данных нет».
- Отсутствие `name`/`manufacturer` — попадает в `missing_fields`.
- Таймаут LLM — один повтор, далее `RuntimeError` → 502 в API.
- Невалидный JSON от LLM — извлечение объекта из markdown-обёртки, иначе correction-проход.

## Ограничения MVP

- Проверка «нет выдуманных характеристик» гарантирует только соответствие входу; смысловую точность формулировок финально смотрит человек.
- Нет RAG по каталогу, glossary, human review UI, A/B оценки текстов.

## Что улучшить дальше

RAG по каталогу как источник фактов; glossary терминов КИП; LLM-as-judge для оценки стиля; батч-UI для контент-менеджера; A/B качества текстов; schema registry.

## Перенесённые продовые практики

Structured output (как JSON-state субагентов), guardrail-цикл «код проверяет → модель исправляет» с лимитом попыток, пакетный прогон на фиксированных входах — подход, который я применял в продовой LLM-системе поддержки (см. сопроводительное сообщение).
